# Auto-ABM 论文中文译稿

## 摘要

Agent-based modeling (ABM) 研究由局部智能体决策涌现出系统级模式的过程。随着 ABM 在计算社会科学、流行病学、经济学和复杂系统研究中变得越来越重要，它的实践成本也在上升：研究者需要花大量时间把假设转化为可执行模型，运行和比较仿真，追踪机制，并打包可复现证据。大语言模型可以加速编程，但很多 ABM 工作流仍然把假设、Trace、解释、实验和导出产物分散在同一个研究循环之外。本文提出 Auto-ABM，这是一个 AI 原生、以仿真为中心的 ABM 研究工作台。Auto-ABM 围绕带版本的仿真对象组织多个专门研究智能体，底层由确定性 Mesa 内核和 Trace 账本支撑。系统在同一工作流中支持机制提出、模型形式化、执行、基于 Trace 的解释、自适应实验和 ODD 对齐导出。覆盖八类 ABM 任务的计划基准中，草稿估计显示它在可执行性、机制有效性、证据 grounding、实验设计和复现报告等评分维度上优于以代码为中心的基线。

## 1 引言

ABM 是研究复杂系统的重要方法，它用异质智能体之间的局部交互解释宏观模式。随着研究者希望表达适应、空间结构、网络效应和政策干预，ABM 的价值愈发明显。但 ABM 研究仍然很耗时：一个完整研究需要把问题转化为机制，编码机制，校验假设，比较运行，解释 Trace，并记录成他人可以检查的模型说明。

现有工具可以生成模拟器代码，或辅助某个建模环境。这降低了编程门槛，却很少改变研究对象的组织方式。脚本仍然是中心，Trace、ODD 描述、解释、实验计划和复现包经常在运行之后才被拼接，导致关于涌现行为的结论难以审计。

Auto-ABM 从仿真出发。在 ABM 研究中，持久对象不是脚本，而是带版本的仿真：它绑定假设、参数、运行、Trace、解释、实验和可导出的证据。系统把语言模型视为受对象约束的研究协作者。假设智能体提出候选机制，建模智能体形式化选定候选，执行智能体调用确定性内核，证据智能体读取 Trace 区间，实验智能体设计扫描或干预，文档智能体维护 ODD 描述。所有角色通过同一 Trace 账本协作，因此解释语言位于可执行证据之后。

本文贡献包括：以仿真为中心的 LLM 辅助 ABM 工作流；围绕带版本仿真对象协作的多智能体编排协议；将确定性分析与自然语言叙述分离的 Trace-grounded 解释机制；以及把机制提出、模型执行、解释、实验和 ODD 导出整合在一起的 AI 原生软件系统。

## 2 相关工作

ABM 通过指定局部规则并观察群体行为来研究复杂适应系统。NetLogo 和 Mesa 等工具让模型可执行，ODD 协议为模型描述和复现提供标准。Auto-ABM 延续这一传统，但把对话系统创建、修改、运行和导出的单位设为仿真对象，而不是外围代码。

近期 LLM 系统已经能够辅助 NetLogo 建模或通过验证器迭代生成 ABM 代码。这些工作说明语言模型可以把自然语言场景转为可运行模型，但重点通常仍在模型构建，而不是 ABM 研究的完整证据生命周期。Auto-ABM 借鉴推理与工具使用交替的 agentic 范式，同时把行动空间约束为 ABM 研究角色和证据对象。其核心差异在于：解释、图表和实验都必须解析到已记录的仿真 Trace 上。

## 3 系统总览

Auto-ABM 是一个面向 ABM 的桌面科研工作台。它的核心抽象是带版本的仿真，而不是生成程序。一个项目包含一个或多个仿真；每个仿真绑定模型规格、ODD 文档、界面状态、运行记录、Trace、实验计划、解释和导出产物。正文中预留了一个四截图总览图，占位分别对应研究工作区、仿真画布、机制图谱和实验工作区。

### 3.1 设计原则

系统有四个原则。第一，Auto-ABM 以仿真为中心，代码只是实现细节。第二，Trace 是事实来源，指标、事件、机制触发和空间快照都会写入运行证据，并被图表、解释和导出复用。第三，可执行核心是确定性的，一次运行由模型版本、随机种子、参数快照和内核版本共同标识。第四，语言生成受到证据约束，被引用的 tick、指标、机制和事件必须存在于选定 Trace 区间中。

系统也把 ODD 协议作为文档主干。ODD 文档由模型规格派生，并与模型版本绑定。模型结构变化时，Auto-ABM 更新 ODD 草稿并尽量保留用户撰写内容，使模型描述成为工作流中的活对象。

### 3.2 架构

Auto-ABM 有三层。交互层呈现对话、仿真视图、Trace 解释、实验控件和 ODD 文档。协调层维护带版本的项目状态，调度角色化行动，并记录运行和导出的溯源信息。内核层基于 Mesa，执行形式化模型规格、输出 Trace、派生机制图并运行批量实验。这样的分离让界面保持响应，同时避免可视化状态成为模型行为的事实来源。

### 3.3 端到端数据流

典型会话从研究问题开始。假设智能体提出候选机制，并给出预期宏观行为和 ODD 风格理由。用户选择候选后，建模智能体将其形式化为仿真规格，执行智能体记录带版本运行。随后用户可以调整参数、检查个体、选择 Trace 区间、请求解释、配置实验并导出复现包。正向和逆向路径共用同一个 Trace 层；无论从机制出发还是从目标现象出发，关于模型行为的结论都来自真实运行和 Trace 记录。

## 4 方法

### 4.1 研究生命周期概览

当前系统把研究生命周期分为六个阶段，并为每个阶段指定一个具有明确证据责任的研究角色。正文只概述这一设计，完整生命周期表移至附录。草案阶段生成候选机制和预期宏观模式；形式化阶段生成带版本规格、参数约束和 ODD 草稿；执行阶段产生运行记录、指标序列、空间快照和 Trace 账本；解释阶段生成机制活动、归因流和带引用解释；实验阶段生成扫描设计、干预计划和结果面板；发布阶段维护 ODD、复现包和溯源清单。

### 4.2 以仿真为中心的多智能体编排

**角色分工。** Auto-ABM 采用推理与外部行动交替的 agentic 模式，但行动空间围绕 ABM 研究角色组织。假设智能体扩展搜索空间，为同一现象提出多个机制族。建模智能体收敛这一空间，把选定提案转化为包含智能体类型、状态变量、环境假设、机制、观测指标和初始化条件的显式规格。执行智能体把规格交给确定性内核，并记录版本、种子、参数快照和运行溯源。

**证据交接。** 下游角色只在存在真实运行后工作。证据智能体把选定 Trace 区间转化为机制活动、状态转移归因、拐点和反事实比较。语言叙述器只接收结构化证据包，而不是自由发明测量结果。实验智能体设计参数扫描或定时干预，并把结果视图绑定到已存储运行。文档智能体更新 ODD 叙述并准备复现包。因此，同一个 Trace 区间可以同时出现在图表、机制图谱、归因视图和解释文本中，而不复制事实来源。

工作台支持研究、对话和自主探索三种模式。本文评估聚焦研究模式，因为它是最能与现有建模辅助系统比较的端到端路径。候选仿真先以多样机制草案生成，再映射到可执行模型族。当前库包括传染扩散、隔离、山火、有限信任意见、创新扩散、公共品合作、阈值影响和平台谣言治理。

### 4.3 机制图谱与基于 Trace 的解释

方法上的关键选择是把解释拆成两层。第一层是确定性的：给定模型规格，内核派生机制图，其节点表示智能体类型、状态变量、参数、机制和观测指标，边来自显式结构关系或规格中的引用。因此，图边记录的是模型结构，而不是大模型生成的因果断言。

第二层读取运行 Trace。Trace 包含指标观测、事件、机制触发和可选空间快照。协调层计算机制活动、状态转移归因、拐点和反事实比较。语言模型只接收选定 Trace 区间、相关 ODD 段落和机制引用组成的结构化上下文。生成后，引用校验器检查每个 tick、指标值、事件名和机制引用是否存在于上下文中；无法支持的陈述会被拒绝或标为推测。

### 4.4 自适应深度实验工作区

ABM 分析经常从单次运行推进到参数扫描、干预和稳健性检查。Auto-ABM 让实验智能体合成声明式实验视图，指定控件、扫描变量、图表意图和首选指标。交互层把规格渲染为可操作控件和结果面板，协调层负责执行和数据绑定。

这种设计避免大模型生成分析时常见的失败模式。实验智能体不提供图表数据，而是提供声明式视图请求，说明来源运行或实验以及需要的字段。协调层根据真实运行记录解析请求并拒绝缺失字段。批量实验由内核展开为运行计划，在受控种子下执行，并持久化到同一个仿真对象中。

### 4.5 完整性机制

系统包含多个完整性 gate。规格 gate 检查模型形状、观测指标可用性、参数范围和 ODD 一致性。解释 gate 根据 Trace 证据校验引用。可视化 gate 把图表请求解析到已存储运行并拒绝伪造字段。模式 gate 在对话模式中阻止状态变更。审批 gate 会在结构性模型修改、大批量运行、破坏性覆盖和复现包导出前请求确认。这些小而明确的检查比一句宽泛的“保持忠实”更容易审计。

## 5 实验

最终实验将衡量 Auto-ABM 是否提升 LLM 辅助 ABM 工作的质量、可解释性和可复现性。由于受控实验尚未运行，本节数字只用于固定实验设计和图表版式，提交前必须替换为真实结果。

### 5.1 任务与系统

评估使用八类 ABM 任务：Schelling 隔离、SIR 传播、平台谣言治理、Granovetter 阈值级联、Bass 创新扩散、有限信任意见动力学、公共品合作和山火扩散。每个任务要求工作流实例化可运行模型，产生至少一次运行，解释选定区间，运行扫描或干预实验，并导出复现产物。完整协议图已移到附录，正文保留主结果表和主结果图。

对比四种工作流：Direct Python 让大模型从任务提示直接写 Python/Mesa 脚本；NetLogo generation 让大模型生成 NetLogo 风格模型和运行说明；Harness 使用带测试和命令执行的一般编码智能体循环；Auto-ABM 使用本文系统。每个工作流会在 Claude Opus 4.6、DeepSeek-V4 和最终实验时可用的最新 Qwen 模型上运行。

### 5.2 指标

- **Executable validity.** 以五分制衡量工作流是否产生可运行模型、完整运行和所需下游产物。
- **Model quality.** 多个盲化 LLM judge 以五分制评分模型结构、假设和观测指标是否匹配任务科学意图，并取平均分。
- **Mechanism validity.** 多个盲化 LLM judge 以五分制评分机制是否合理，并是否体现在可执行模型中。
- **Evidence grounding.** Trace 校验器检查被引用事实，LLM judge 进一步评分解释是否恰当地使用这些证据。
- **Experiment quality.** 多个盲化 LLM judge 以五分制评分扫描或干预是否有意义、可执行，并且与研究问题相连。
- **Reproduction completeness.** 以五分制检查导出包是否包含模型规格、ODD 文档、运行元数据、种子、Trace、实验计划和溯源清单。

综合分数是上述六个维度的非加权平均。

### 5.3 主结果

当前占位估计预期呈现如下模式：直接生成容易产生看似合理却缺少 Trace 支撑解释的代码；NetLogo generation 更符合 ABM 惯例，但仍把模型构建、解释和实验报告分开；Harness baseline 在可执行性上更强，因为它能迭代修复失败，但输出仍以代码为中心；Auto-ABM 预期在证据 grounding、实验质量和复现完整性上更高，因为内核、Trace、ODD、实验运行器和导出清单在所有任务中共享。

## 6 结论

Auto-ABM 把 LLM 辅助 ABM 重新组织为以仿真为中心的研究工作流。它不把代码生成当作终点，而是把仿真、运行、Trace、ODD 文档、实验和导出保持为相互链接的研究对象。其主要贡献是专门研究智能体、确定性 Mesa 内核、由规格派生的机制图谱、经过证据校验的解释和自适应实验视图的结合。研究者可以在同一界面中从问题进入可运行模型，检查涌现行为背后的证据，并导出可复现产物。

## Limitations

本文稿描述的系统仍在为最终投稿准备。受控评估尚未运行，第 5 节的数值是占位。当前内核覆盖常见 ABM 模型族，但不是适用于所有领域的通用模拟器。机制图由显式规格引用派生，可能漏掉自定义行为实现中的隐含依赖。证据校验能检查被引用的 Trace 事实，但不能证明叙述解释是唯一合理解释。自主探索是产品方向和部分工作流，主要评估应聚焦已经端到端打通的研究模式闭环。

## Ethics Statement

Auto-ABM 用于支持建模和解释，而不是认证政策结论。ABM 结果依赖关于智能体、环境和机制的假设。工作台通过 ODD 文档、Trace 证据和复现导出让这些假设更可见，但领域验证仍由用户负责。生成解释应被视为链接到 Trace 证据的分析摘要，而不是模型之外的因果证明。
